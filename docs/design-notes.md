# 设计注记 —— v0.1.0 实现中的工程决策

## 1. 为什么工厂闸门用嵌套解释器（子进程）而不是进程内调用

主控进程在启动时静态 import 了全部模块；minted 专家是运行时产物，无法回到已加载的
模块图。嵌套 `bun dhv run <expert.hsl>` 让「机器生成的代码被真实解释器验收」成为
不争的事实——闸门没有模拟，check 与 fixture 验收都是真的。

副作用是免费的蓝绿：磁盘专家每次派单都从磁盘加载最新版，在岗会话跑旧版、新派单
自动加载新版的语义不需要任何额外机制。

## 2. 客观闸门先行（结构性优先于裁判）

review() 的判定序：预算遵守（机械）→ 覆盖率线（机械）→ 语义裁决（模型）。
首轮低覆盖直接触发机械 Revise（意见取 worker 自报的 remedy 提示——类型化报告
强制摘要的收益：意见即数据，跨运行可精确复发比对），只有机械闸门全过才花模型调用。

## 3. 复发计数必须跨运行持久化

运行内 recurrence 只能证明「本轮复发」，补丁升级判据需要「历史复发」——
runtime/recurrence.json 以 expert::note 为 key 持久化。同理，固化的观测账本
（observations）也必须持久化：单轮内同一输入往往只出现一次，观测计数跨轮累计
才可能达到冻结阈值。这是「任务记忆」的最小可运行形态。

## 4. 剧本轨道的进程边界

每次 dhv run 是独立进程，fixture 轨道索引从 0 重算。跨轮剧本设计的硬约束：
**各轮的第一条 miss 必须落在同一轨道位置且取值一致**。run-notices.json 把
unknown 日期排在通知首位正是为此（run A 的 obs1 与 run B 的 obs2 共享位置 0）。

## 5. 验收语义 ≠ 执行语义

嵌套执行的 ok 判定（run.json）只回答「执行是否成功」；覆盖率闸门只施加于工厂
Exam 与补丁 smoke（样本必须达标）。真实派单首轮低覆盖是合法的 Revise 语义——
监督回路才是覆盖率的主人。

## 6. 直连为什么是 fn 而不是 graph

G1 要求 graph 恰含 AgentLoop；单轮直连会话套循环是过度仪式。诚实呈现为
async fn（多轮直连升级为 graph 时再引入循环——那时循环有真实语义）。

## 7. mint_hsl 轨道与 factory/stock/ 的逐字一致

scripted 剧本 = 某次真实生成响应的录制。factory/stock/record-validator.hsl
是这份录制的人工抽查存档（设计文档「生成器同时出题又答题」风险的兜底机制）。
make-fixture.ts 每次从 stock 文件读取源码嵌入轨道——两者不可能静默漂移。
